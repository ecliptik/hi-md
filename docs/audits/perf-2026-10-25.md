# Performance fixes, measured: 2026-10-25

The audit round of 2026-10-25 ([README](README-2026-10-25.md)) estimated its performance costs from reading the code. This round measured eight of them before and after fixing them, on branch `perf/hot-paths` (from `fix/navidrome-placeholder` at 4a63019).

## Method

- **Where:** the iPhone 17 Pro simulator, iOS 27.0 (24A434), on a MacBook Pro M1 Max (32 GB) with Xcode 27.1. Other builds were running at the same time.
- **Build:** Release (`-O`, whole module) with `ENABLE_TESTABILITY=YES`, so the tests can reach internal code. Debug numbers would be several times higher.
- **Suite:** `MinidiscTests/PerformanceBenchmarks.swift`, which normal runs skip. Run it with:

      TEST_RUNNER_MINIDISC_BENCH=1 xcodebuild test -scheme MinidiscTests -configuration Release \
        ENABLE_TESTABILITY=YES -destination '<simulator>' -parallel-testing-enabled NO \
        -only-testing:MinidiscTests/PerformanceBenchmarks

- **Timing:** each benchmark does one warm-up run, then times 3 to 9 runs with `ContinuousClock` and reports the median. The suite was run three times before the fixes and three times after. The tables give the median of those per-run medians.
- **Before:** measured on unchanged code. For paths that are private to a view, the baseline times a verbatim copy in `MinidiscTests/LegacyHotPaths.swift`. Where the app's own code could be called as well (online ranking), the copy and the app agreed within 1%. The equivalence tests use the same copies.
- **Caveat:** simulator numbers are indicative only. They run on the Mac's cores, not an iPhone's. Verify on a device with Instruments before relying on the absolute values. The ratios are more trustworthy than the milliseconds.

## Results

### 1. Search ranking (Swift performance CRITICAL and H1, SwiftUI H5)

Each candidate is now scored once, against a query normalised once, and sorted on the stored score with the same comparators. The offline snapshot normalises its titles when it loads, off the MainActor. `SearchViewModel` stores the ranked matches and re-ranks only when the results, the playlists or the normalised query change.

| Path | Scale | Before | After |
|---|---|---|---|
| Offline ranking, 'love' (one keystroke) | 4,998 items | 136.7 ms | 9.8 ms |
| Offline ranking, 'blue night' | 4,998 items | 81.8 ms | 8.2 ms |
| Offline ranking, 'ångström' | 4,998 items | 105.0 ms | 8.9 ms |
| Offline body pass, same query and snapshot | 4,998 items | 136.7 ms | 0.001 ms |
| Online ranking, 'love' | 350 results + 40 playlists | 66.8 ms | 4.8 ms |
| Online ranking, 'blue night' | 350 results + 40 playlists | 75.0 ms | 5.0 ms |
| Online body pass (ranked twice before) | 350 results + 40 playlists | 135.4 ms | 0 (stored) |
| Building the offline search entries, once per snapshot | 4,998 items | none | 20.9 ms, off the MainActor |

The order of results is unchanged: the order-equivalence tests compare 29 queries against the old code, online and offline.

### 2. Queue rows on a track change (SwiftUI C1)

Rows hold only their index, song and identity. The `QueueTrackSelection` is built when a row is tapped, removed or dragged. Occurrence counts are cached per queue revision, and rows per generation, revision and position. The list shows 200 upcoming songs, with "Show More" for each further 200. That adds one string, translated into the catalogue's eight languages. Dropping a dragged row below the last row shown inserts it there, not at the end of the hidden queue.

| Path | Scale | Before | After |
|---|---|---|---|
| Track change | 50,000 songs | 37.3 ms | 0.018 ms |
| Track change | 200,000 songs | 164.3 ms | 0.018 ms |
| Queue edit (counts rebuilt) | 50,000 songs | 37.3 ms | 3.2 ms |
| Queue edit | 200,000 songs | 164.3 ms | 19.7 ms |
| Rows the `List` diffs on each change | 200,000 songs | 199,989 | 200 |

The engine, crossfade, gapless, recovery and queue suites passed before and after: 217 tests before, then 227 with the new row tests, all green.

### 3. Placeholder detection (Swift performance H2, concurrency M6)

The check now runs off the MainActor:
- for disk hits, inside the detached decode task;
- for the untagged-file fallback in `CoverArtView`, in its own detached decode;
- for network covers, in a `@concurrent` hop after the injectable decoder.

It draws into a stack buffer with a static colour space and a static radius table, and sums each region in one pass with no pixel arrays. The verdicts are bit-for-bit identical: the sums are added in the same order as before, and a test compares old and new on 82 images.

| Path | Scale | Before | After |
|---|---|---|---|
| MainActor time, per cover | 240 px thumb | 0.046 ms | 0 |
| MainActor time, per cover | 1,200 px hero | 0.40 ms | 0 |
| The check itself, per cover | 240 px thumb | 0.046 ms | 0.042 ms |
| The check itself, per cover | 1,200 px hero | 0.40 ms | 0.37 ms |

Most of the remaining cost is CoreGraphics downsampling the image to 32×32, which has to stay as it is to keep the verdicts identical. The audit's estimate of 70 KB of churn per cover is gone. The gain is moving the check off the MainActor, not making the check cheaper.

### 4. CoverArtView mount path (SwiftUI H4)

The body reads the RAM cache once per id, tier and upload version, as a snapshot of the unobserved cache. The task then leaves the view's state alone when the body is already showing that image. The `.empty` placeholder is now a static rounded rectangle.

The timings come from 60 covers mounted in a `UIHostingController` with RAM hits, measured with a temporary body counter that has since been removed. Each figure is the median of 12 mounts before and 18 after.

| Path | Scale | Before | After |
|---|---|---|---|
| Body passes | 60 covers | 120 | 60 |
| SkeletonBlock bodies (each with a repeating animation) | 60 covers | 120 | 0 |
| First layout | 60 covers | 38.9 ms | 7.0 ms |

Skipped: sharing the `coverArtUploadVersion` observer. Replacing the per-cover `@AppStorage` needs a KVO bridge with a hop to the MainActor, which changes when covers react to an upload. That isn't clean enough for an unmeasured gain.

### 5. `Array(songs.enumerated())` copies (SwiftUI H3)

The six `ForEach` call sites now iterate `songs.enumerated()` directly:
- SongsListView;
- FavoritesView;
- PlaylistDetailView, twice;
- AlbumDetailView;
- the search song section.

No `.id` modifiers were dropped. SongsListView's and FavoritesView's are the alphabet bar's `scrollTo` targets, and the other sites have none.

| Path (walking every row identity, as ForEach does) | Scale | Before | After |
|---|---|---|---|
| Body pass | 5,000 songs | 1.02 ms | 0.45 ms |
| Body pass | 200,000 songs | 52.5 ms | 18.2 ms |

The remaining time is hashing the IDs, which ForEach does either way. The copy that was removed held about 330 bytes per song.

### 6. SongSelectionSheet (SwiftUI H2)

`SongSelectionCollection` deduplicates once per request and normalises each song's search text the first time a query needs it. The filtered songs and their ID set are cached per request and normalised query.

### 7. Track-change work in PlayerService (Swift performance H5 and H6)

- `evaluateAutoExtend` takes the queue by reference in its MainActor read, and builds the ID set on the PlayerService actor only after the cheap guards pass.
- `SessionPayload` carries `PlayerState.queueRevision`. `PlaybackSessionService` keeps the stored queue blob when that revision has already been saved, and reuses one encoder.

| Path | Scale | Before | After |
|---|---|---|---|
| MainActor work in `evaluateAutoExtend`, per track change | 20,000 songs | 0.91 ms | 0.000 ms |
| Session save after a skip or seek | 20,000 songs | 86.8 ms | 7.6 ms |
| Session save after a queue change | 20,000 songs | 86.8 ms | 77.5 ms (unchanged: the queue has to be written) |

Skipped: comparing queues by identity in `play(tracks:startIndex:)`. The coordinator limited PlayerService edits to `evaluateAutoExtend` and the session save, to keep clear of `fix/playback-buffering`. That comparison measured 0.24 ms at 20,000 songs, so little is lost. Engine scheduling is untouched.

The engine, crossfade, gapless, recovery, queue, session and restore suites passed: 239 tests, 0 failures.

### 8. Memory (memory H-1 and M-1)

- `LidarrImageStore` is an `NSCache` limited to 120 covers and 48 MB, costed by decoded bytes.
- `ArtworkImageCache` keeps its 110-entry LRU and adds a 96 MB budget. When the cache is over budget, it evicts the oldest hero rather than list thumbnails.
- `AppContainer` registers one memory-warning observer. It drops the hero tier and empties the Lidarr store.

| Path | Scale | Before | After |
|---|---|---|---|
| Lidarr covers retained | 300 covers of 1,000 px | 1,144 MB (all 300) | 46 MB (12) |
| Artwork covers retained | 110 heroes, then 110 thumbs, then 40 heroes | 235 MB (110) | 93 MB (109) |
| Worst case for the artwork cache | 110 heroes | about 634 MB | 96 MB or less |

These are decoded bytes as the caches cost them, not the process footprint.

## Tests

The full unit suite ran once, in Debug, on the branch head: 1,213 passed, 5 failed and 11 were skipped. The skipped tests are the opt-in benchmarks.

The five failures all hit their polling deadlines at the same moment, about 12 s into a run that shared the machine with other builds. That is the shared-MainActor stall described in testing H2 and H6. Each passed in two isolated reruns:
- three tests in `ArtworkImageCacheConcurrencyTests`;
- `PlaybackPresentationTests.briefTrackLoadingDoesNotFlashAStatusAndPauseCancelsDelayedStatus`;
- `LyricsViewModelScrollTests.isUserScrolling_resetAfter5Seconds`.

There is no `MinidiscMac` scheme on this base, so no native Mac build was made. The new code uses only UIKit and SwiftUI API that Mac Catalyst also has.

## Verify on a device

- **Search:** type a search offline with about 5,000 downloads, in Instruments with Time Profiler and Hangs.
- **Queue:** open the queue with a 200,000-song Smart Shuffle or Songs-tab queue, and skip quickly. Listen for gapless and crossfade at each skip.
- **Covers:** scroll fast through Albums with a cold cache and then a warm one, using the Animation Hitches instrument.
- **Memory:** browse about 200 Lidarr covers, then open the full player on about 20 albums. Watch Allocations, and trigger a memory warning from the simulator's Debug menu.
